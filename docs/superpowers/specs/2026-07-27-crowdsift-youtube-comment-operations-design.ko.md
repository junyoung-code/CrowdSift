- **시각 방향 선택일:** 2026-07-28
- **작성 방식:** `superpowers:brainstorming`
- **우선 대상:** 데스크톱 웹
- **확장 기준:** [첫 실제 수직 슬라이스 설계](./2026-07-23-crowdsift-real-vertical-slice-design.ko.md)
- **선택된 시각 기준:** [대화 중심 워크스페이스](../../../references/crowdsift-ui/2026-07-28-conversation-workspace.png)

## 1. 결정 요약

CrowdSift를 브라우저 확장 프로그램이나 YouTube 화면의 복제품으로 만들지 않는다. 공식 YouTube Data API를 사용하는 독립 웹 앱으로 만들고, CommentShark 레퍼런스의 작업 효율과 YouTube 댓글의 익숙한 정보 구조를 결합한다.

최종 제품 범위에는 다음 기능을 모두 포함한다.

1. 실제 YouTube 작성자 프로필, 댓글, 답글과 영상 문맥을 가져오는 Comment Inbox
2. `안전 / 주의 / 위험`과 댓글 의도별 검색·필터·정렬
3. 댓글 스레드 안에서 작성하는 수동 답글
4. 답글 템플릿
5. 크리에이터 말투를 참고하는 AI 답글 초안
6. 실제 댓글로 먼저 시험하는 Moderation/Reply Rules
7. 크리에이터가 승인하는 답글 및 moderation 대기열
8. CrowdSift가 수행한 작업의 활동 피드와 운영 대시보드
9. 같은 작성자의 과거 대화를 모아 보는 Audience 화면

모든 기능을 한 번에 구현하지는 않는다. 먼저 기존 기준 문서의 핵심 흐름인 `YouTube 연결 → 영상 선택 → 댓글·답글 수집 → AI 분류 → DB 저장 → Comment Inbox`를 실제 데이터로 완성한다. 그다음 실제 답글 쓰기, AI·템플릿, 규칙, Audience·대시보드를 순서대로 추가한다.

승인 없는 자동 답글 게시와 자동 삭제는 현재 범위에 포함하지 않는다. 규칙은 초안 생성, 검토 대기열 추가, 알림까지 자동화할 수 있지만 외부 쓰기 작업은 사용자가 실행 내용을 확인한 뒤에만 수행한다.

2026-07-28 Product Design 시각 탐색에서 두 번째 방향인 `대화 중심 워크스페이스`를 선택했다. 댓글 목록보다 선택한 실제 스레드와 답글 작성 공간을 크게 두고, 분석은 좁은 보조 영역에 배치한다.

## 2. 해결하려는 사용자 문제

현재 Comment Inbox 목업은 YouTube 댓글과 시각적·정보적으로 거리가 있고, 실제 작성자 프로필과 대화 관계가 충분히 드러나지 않는다. 사용자는 별도 화면을 보더라도 다음 세 가지를 즉시 믿을 수 있어야 한다.

- 지금 보는 작성자와 댓글이 실제 YouTube에서 가져온 데이터다.
- 최상위 댓글과 답글의 관계를 잃지 않았다.
- CrowdSift에서 답글을 게시하면 선택한 크리에이터 채널의 공개 답글로 YouTube에 등록된다.

동시에 CrowdSift의 차별점인 유해 원문 보호를 유지해야 한다. YouTube와 익숙하게 보인다는 이유로 `주의`와 `위험` 댓글의 공격적 원문을 목록에서 바로 노출하지 않는다.

## 3. 검토한 접근 방식

### A. YouTube DOM 위에 확장 프로그램 UI 삽입

장점은 YouTube와 가장 비슷하게 느껴지고 사용자가 페이지를 이동하지 않아도 된다는 점이다. 그러나 YouTube DOM 변경에 취약하고, 스크래핑을 사용하거나 YouTube UI에 간섭할 위험이 있으며, CrowdSift의 작업 대기열·AI 분석·감사 로그를 운영하기 어렵다.

**결정:** 채택하지 않는다.

### B. 공식 API 기반 독립 웹 앱

실제 데이터의 출처와 쓰기 작업을 통제할 수 있고, 서버에서 OAuth 토큰·작업 상태·AI 결과·감사 로그를 안전하게 관리할 수 있다. YouTube 화면을 그대로 복제할 수는 없지만, 댓글 카드의 익숙한 계층과 실제 프로필·영상 썸네일을 사용할 수 있다.

**결정:** 현재 권장안이자 구현 기준이다.

### C. 웹 앱과 선택적 보조 확장 프로그램

핵심 시스템은 웹 앱에 두고, 나중에 별도 확장 프로그램이 CrowdSift 작업함으로 이동하는 단축 동선만 제공하는 방식이다. YouTube UI에 내용을 삽입하지 않고 별도 Side Panel을 사용하더라도 정책·유지보수 검토가 추가로 필요하다.

**결정:** 핵심 제품이 검증된 뒤 별도 기획으로만 재검토한다.

## 4. 레퍼런스 화면에서 가져올 기능

| 레퍼런스 | CrowdSift 기능 | 초기 동작 |
|---|---|---|
| Rules | 조건, 대상 영상, 실행 작업, 승인 방식과 알림을 문장형 규칙으로 설정 | 실댓글 dry-run과 승인 대기열만 제공 |
| Dashboard | 답글, moderation, 건너뜀, 실패와 동기화 활동을 시간순으로 표시 | 실제 `activity_events`만 집계 |
| Audience | 신규·재방문 작성자와 과거 대화를 한곳에서 확인 | 수집한 댓글과 제공되는 작성자 채널 ID 기준 |
| AI Replies | 여러 답글 초안, 재생성, 편집, 게시 | 사용자 확인 전에는 YouTube에 쓰지 않음 |
| Comment Inbox | 의도, 위험도, 영상, 작성자, 응답 상태별 검색·필터 | 실제 수집 데이터만 표시 |
| 선택한 대화 중심 UI | 아이콘 레일, 댓글 대기열, 넓은 대화·작성 공간, 접을 수 있는 분석 요약 | CrowdSift 브랜드와 안전 UX로 재구성 |

레퍼런스의 자산, 로고, 문구, 정확한 화면 구조는 복제하지 않는다. 실제 YouTube 출처 데이터와 CrowdSift가 생성한 분석·추천은 시각적으로 명확히 구분한다.

## 5. 공식 API로 가져올 수 있는 댓글 정보

댓글과 답글에서 다음 필드를 사용할 수 있다.

| 화면 정보 | YouTube 필드 | 처리 원칙 |
|---|---|---|
| 작성자 표시 이름 | `snippet.authorDisplayName` | API 반환값을 표시 |
| 프로필 이미지 | `snippet.authorProfileImageUrl` | 이미지 파일을 영구 복제하지 않고 URL과 갱신 시각 관리 |
| 작성자 채널 | `snippet.authorChannelId`, `authorChannelUrl` | 제공되지 않을 수 있으므로 nullable |
| 표시 댓글 | `snippet.textDisplay` | `textFormat=plainText`로 요청하고 출처 표시 텍스트로 저장 |
| 진짜 원문 | `snippet.textOriginal` | 인증 사용자가 댓글 작성자인 경우에만 반환될 수 있으므로 nullable |
| 좋아요 수 | `snippet.likeCount` | YouTube가 반환한 값만 표시 |
| 작성·수정 시각 | `publishedAt`, `updatedAt` | 두 값이 다르면 `수정됨` 표시 |
| 부모 관계 | `snippet.parentId` | 답글을 최상위 댓글과 연결 |
| moderation 상태 | `moderationStatus` | 소유자 권한과 응답에 포함된 경우에만 표시 |
| 답글 가능 여부 | `commentThread.snippet.canReply` | `false`이면 작성창 비활성화 |
| 답글 수 | `commentThread.snippet.totalReplyCount` | 누락 답글 추가 조회 판단에 사용 |

`textDisplay`는 링크가 영상 제목으로 바뀌는 등 최초 입력과 다를 수 있다. 따라서 다른 시청자의 댓글을 “100% 원문”이라고 표시하지 않는다. UI에서는 `YouTube 표시 내용` 또는 `출처 댓글`이라고 부르고, `textOriginal`이 실제로 반환된 경우에만 `원문`이라고 표시한다.

`commentThreads.list`의 `replies`는 전체 답글이 아닐 수 있다. `totalReplyCount`와 받은 답글 수가 다르면 `comments.list(parentId=최상위댓글ID)`를 페이지네이션해 가능한 답글을 모두 가져온다.

첫 검증 배치는 최상위 댓글 20~50개와 그 스레드에서 API로 가져올 수 있는 모든 답글이다. 이것은 제품의 영구 상한이 아니다. 실제 연결이 검증된 뒤 같은 page token 기반 서비스에 `더 가져오기`와 정기 재동기화를 연결해 선택한 영상의 나머지 댓글 스레드를 확장 수집한다.

이 설계에서 `프로필`은 댓글 응답이 제공하는 표시 이름, 프로필 이미지 URL, 작성자 채널 ID와 채널 URL을 뜻한다. 작성자 소개, 구독자 수나 비공개 채널 정보까지 가져온다는 뜻이 아니다.

## 6. 핵심 사용자 흐름

```text
CrowdSift 로그인
→ YouTube 읽기 권한 연결
→ 소유 채널 하나 선택
→ 영상 하나 선택
→ 최상위 댓글 20~50개와 그 답글 수집
→ 출처 스냅샷 저장
→ 안전 / 주의 / 위험과 댓글 유형 분석
→ Comment Inbox에서 실제 프로필·스레드 확인
→ 댓글 또는 답글을 선택
→ 직접 작성 / 템플릿 / AI 초안 중 하나 선택
→ 작성자가 문구와 게시 채널을 확인
→ 필요한 경우 YouTube 쓰기 권한 추가 동의
→ 다시 게시 내용을 확인
→ YouTube에 답글 등록
→ YouTube가 반환한 답글 ID와 작업 결과 저장
→ 스레드 재동기화
```

OAuth 동의 직후 답글을 자동 게시하지 않는다. 권한 동의를 마치면 작성 중인 초안을 복원하고 게시 확인 화면으로 돌아온다.

## 7. Comment Inbox 정보 구조

### 7.1 데스크톱 레이아웃

선택된 방향은 [대화 중심 워크스페이스](../../../references/crowdsift-ui/2026-07-28-conversation-workspace.png)다. 모든 기능을 한 화면에 광고하지 않고 `목록에서 댓글 선택 → 스레드 이해 → 답글 작성 → 게시 전 확인`에 집중한다.

`1440px` 기준으로 다음 네 영역을 같은 작업 표면에 배치한다.

1. **아이콘 내비게이션 레일**
   - 약 `72px`
   - Comment Inbox, 승인 대기열, Rules, Audience, Activity
   - 알림과 설정
   - 현재 위치는 색상 외에 배경과 텍스트로도 표시
2. **댓글 대기열**
   - 약 `390px`
   - 검색
   - `안전 / 주의 / 위험`
   - 최신순과 미답변 우선
   - 실제 프로필, 표시 이름, 짧은 순화·출처 미리보기, 영상 썸네일, 의도, 응답 상태
   - 선택된 행은 카드로 띄우지 않고 왼쪽 선택선과 약한 배경으로 구분
3. **대화 워크스페이스**
   - 남은 폭의 대부분을 사용
   - 상단 영상 썸네일, 제목, 채널, YouTube 출처와 `YouTube에서 보기`
   - 최상위 댓글과 한 단계 답글
   - 유해 출처 댓글 경고와 `출처 댓글 확인`
   - 화면 하단에 붙는 직접 작성·템플릿·AI 초안 작성기
   - 기본 작성 행동은 `게시 전 확인`
4. **분석 요약 레일**
   - 약 `200px`
   - 현재 검토 등급
   - 댓글 의도와 유용한 신호
   - 사람 확인이 필요한 이유
   - 긴 근거, 규칙 편집과 moderation 이력은 별도 Drawer에서 확인

분석보다 실제 대화가 넓어야 한다. 작성기는 별도 팝업보다 스레드 아래에 붙여 읽기와 쓰기의 문맥이 끊기지 않게 한다. AI 재작성은 `더 짧게`, `더 따뜻하게`처럼 결과를 예측할 수 있는 보조 행동만 가까이 둔다.

반응형 규칙:

- `1440px` 이상: 네 영역을 함께 표시
- `1180~1439px`: 분석 레일을 접을 수 있는 Drawer로 전환
- `1024~1179px`: 아이콘 레일 + 축소된 대기열 + 대화 워크스페이스, 분석은 Drawer
- `1024px` 미만: 대화 워크스페이스를 우선하고 대기열·분석을 각각 Drawer로 전환

모바일 앱은 범위 밖이지만 작은 화면에서도 유해 출처 댓글 경고와 게시 확인을 생략하지 않는다.

선택된 이미지는 정보 구조와 시각 위계를 위한 목업이다. 이미지 안의 프로필, 영상, 댓글과 수치는 실제 연결 데이터가 아니다. 구현 화면에서는 생성된 목업 데이터를 실제 YouTube 데이터처럼 사용하지 않고, 연결 전에는 명확한 빈 상태를 보여준다.

### 7.2 댓글 카드

안전 댓글은 출처 표시 내용을 기본으로 보여준다. `주의`와 `위험`은 다음 순서를 지킨다.

```text
작성자·영상·시각
→ CrowdSift가 생성한 순화 피드백 또는 “유용한 신호 없음”
→ 검토 등급과 이유 코드
→ 경고를 확인한 사용자가 요청할 때만 출처 댓글 표시
```

색상만으로 등급을 구분하지 않는다. 등급 텍스트, 아이콘, 이유를 함께 표시한다. `안전`은 절대적 안전 판정이 아니라 현재 정책과 분석 신뢰도에서 검토 우선순위가 낮다는 의미다.

### 7.3 답글 계층

최상위 댓글 아래에 답글을 한 단계 들여쓰기하고 세로 연결선을 사용한다. YouTube API는 현재 답글에 대한 또 다른 중첩 답글을 지원하지 않는다.

- 최상위 댓글에 답글: 해당 댓글 ID를 `parentId`로 게시
- 기존 답글을 선택해 답장: 같은 최상위 댓글 ID에 게시하고, 사용자가 원하면 `@표시이름`을 문구에 넣음
- UI는 두 번째 경우를 진짜 2단계 중첩 답글처럼 오해하게 표현하지 않음

답글 작성창에는 `이 답글은 YouTube에서 최상위 댓글 아래에 등록됩니다`라는 결과를 미리 보여준다.

### 7.4 YouTube 출처 표시

각 화면에서 다음을 제공한다.

- `YouTube에서 가져옴` 출처 표시
- 영상과 댓글을 여는 `YouTube에서 보기`
- YouTube 출처 값과 CrowdSift 분석값의 다른 배지
- YouTube 브랜드 가이드에 맞는 귀속 표시

CrowdSift 분석, 위험도, 규칙 점수와 AI 초안을 YouTube가 제공한 정보처럼 보이게 하지 않는다.

## 8. 답글 작성과 YouTube 게시

### 8.1 작성 방법

1. **직접 작성:** 사용자가 빈 작성창에서 입력
2. **템플릿:** 저장된 문구를 삽입한 뒤 편집
3. **AI 초안:** 선택한 댓글과 허용된 스레드 문맥을 바탕으로 2~3개 제안

세 방식 모두 게시 전 같은 확인 흐름을 거친다. AI가 만든 초안은 답글이 아니라 편집 가능한 제안이다.

### 8.2 템플릿

템플릿은 전역 또는 영상별로 저장하며 다음 정보를 가진다.

- 이름과 본문
- `{author}` 같은 검증된 자리표시자
- 적용 영상 범위
- 언어와 톤
- 정렬 순서
- 활성화 상태와 버전

자리표시자를 치환한 최종 문장을 게시 확인 화면에서 보여준다. 사용할 수 없는 작성자 정보는 빈 문자열로 조용히 바꾸지 않고 사용자에게 수정하도록 안내한다.

### 8.3 AI 답글 초안

AI는 다음 입력만 사용한다.

- 선택한 출처 댓글과 허용된 상위 스레드 문맥
- 영상 제목 등 필요한 최소 문맥
- 크리에이터가 설정한 톤·금지 표현
- 사용에 동의한 같은 워크스페이스의 과거 승인 답글

크리에이터별 별도 모델을 학습했다고 표현하지 않는다. 초기 개인화는 버전이 있는 톤 가이드와 같은 워크스페이스의 승인 사례 검색으로 구현한다.

AI는 알 수 없는 사실, 약속, 가격, 일정이나 정책을 만들어내면 안 된다. 답을 위한 정보가 없으면 `크리에이터 확인 필요` 상태와 편집 포인트를 반환한다. 유해 댓글에 대한 초안은 공격적 표현을 반복하지 않으며, 심각한 협박·피싱에는 답글보다 검토·증거 보존을 우선 추천한다.

### 8.4 게시 확인

전송 아이콘을 누른 즉시 API를 호출하지 않는다. 확인 화면에 다음을 표시한다.

- 게시할 크리에이터 채널 이름과 프로필
- 답글 대상 댓글과 영상
- 실제 게시될 최종 문구
- `AI 초안`, `템플릿`, `직접 작성` 출처
- 공개 답글로 YouTube에 게시된다는 설명
- 예상 API 작업 1회

확인 버튼 문구는 `YouTube에 공개 답글 게시`로 한다.

### 8.5 API와 권한

답글은 `comments.insert(part=snippet)`를 사용하고 요청 본문에 다음을 전달한다.

```json
{
  "snippet": {
    "parentId": "TOP_LEVEL_COMMENT_ID",
    "textOriginal": "사용자가 확인한 최종 답글"
  }
}
```

읽기 연결은 `youtube.readonly`로 시작한다. 사용자가 처음 답글 게시 또는 moderation을 실행할 때 `youtube.force-ssl`을 점진적으로 요청한다. 토큰과 클라이언트 비밀값은 서버에서만 암호화해 저장한다.

읽기 요청은 페이지당 기본 1 quota unit, 답글 게시와 댓글 쓰기·moderation 작업은 일반적으로 50 units다. 기본 10,000 units/day 프로젝트라면 다른 API 사용을 모두 제외해도 이론상 약 200회의 50-unit 작업이 상한이므로, 워크스페이스별 사용량과 프로젝트 잔여 예산을 관찰하고 대량 작업 전에 예상 비용을 보여준다.

### 8.6 게시 상태와 중복 방지

`outbound_reply_requests`는 다음 상태를 가진다.

```text
draft
awaiting_confirmation
awaiting_scope
submitting
succeeded
failed
outcome_unknown
cancelled
```

YouTube `comments.insert`에는 CrowdSift의 멱등성 키를 전달할 수 없다. 네트워크가 끊겨 게시 결과를 확인하지 못한 경우 자동 재시도하면 중복 답글이 생길 수 있다.

따라서 `outcome_unknown`은 자동 재시도하지 않는다. 스레드를 다시 조회해 연결 채널이 작성한 동일 문구·근접 시각의 답글을 찾고, 확정되지 않으면 사용자가 중복 가능성 경고를 확인한 뒤 재시도하게 한다.

`답글 시작 시 초안 자동 채우기` 설정은 작성창에 템플릿이나 AI 제안을 미리 넣는 기능일 뿐이다. 이 설정을 켜도 게시 확인이나 YouTube API 호출은 자동으로 실행되지 않는다.

## 9. 안전·주의·위험 판단과 설명

기존 수직 슬라이스의 정의를 그대로 사용한다.

| 등급 | 핵심 기준 | 기본 UX |
|---|---|---|
| 안전 | 충분한 신뢰도에서 중요한 위험, 정책 충돌, 혼합 신호가 발견되지 않음 | 출처 표시 내용을 기본 노출, 낮은 검토 우선순위 |
| 주의 | 비꼼·은어·문맥 의존, 낮은 신뢰도, 공격과 유용한 의견의 혼합, 크리에이터 정책 충돌 | 순화 피드백 우선, 사람 검토 |
| 위험 | 피싱, 신빙성 있는 협박, 심각한 괴롭힘, 강한 공격 또는 증거 보존 우선 신호 | 원문 숨김, 빠른 검토와 증거 보존 |

각 분석에는 최종 등급만 저장하지 않고 다음을 함께 남긴다.

- 댓글 유형
- 신뢰도
- 일치한 결정적 규칙
- 크리에이터 정책 버전
- 모델, 프롬프트와 스키마 버전
- 1차·2차 분석 결과
- 사람이 검토해야 하는 이유 코드
- 추천 조치와 그 근거

사용자가 판단을 수정해도 과거 분석을 덮어쓰지 않고 별도 피드백으로 남긴다.

## 10. Rules 설계

### 10.1 규칙 구성

규칙은 다음 문장 구조로 만든다.

```text
만약 [대상 영상의 댓글]이
[댓글 유형 / 검토 등급 / 키워드 / 규칙 신호]와 일치하면
[AI 초안 만들기 / 템플릿 초안 만들기 / 검토함으로 이동 / 알림 보내기]를 수행하고
[항상 사용자 승인] 후 외부 작업을 실행한다.
```

규칙은 버전이 있는 `draft → tested → active → paused → archived` 상태를 가진다.

### 10.2 Dry-run

규칙을 활성화하기 전에 선택한 실제 댓글 배치로 시험한다.

- 일치 댓글 수와 대표 사례
- 예상 초안과 추천 작업
- `안전 / 주의 / 위험`별 오탐 가능성
- 실행되지 않는 외부 작업
- 예상 quota 사용량

Dry-run은 YouTube에 답글을 쓰거나 댓글 상태를 바꾸지 않는다.

### 10.3 승인 대기열

규칙이 일치하면 `rule_evaluation`과 작업 요청을 만들되 API 호출은 하지 않는다. 사용자는 원문 보호 상태에서 분석 근거, 최종 문구, 대상 채널과 작업 결과를 확인한 뒤 승인·수정·건너뜀을 선택한다.

여러 작업을 일괄 승인하는 기능을 추가하더라도 대상 수, 영상, 작업 종류와 최종 문구를 명확히 보여주고 별도 확인을 받는다.

## 11. Audience 설계

Audience는 공개 프로필을 수집해 사람을 추적하는 도구가 아니라, 연결한 채널에서 이미 수집한 댓글 대화를 다시 찾는 작업 화면이다.

작성자 채널 ID를 사용할 수 있을 때만 안정적인 동일인 키로 사용한다. 사용할 수 없으면 표시 이름이나 프로필 사진으로 동일인이라고 추정하지 않는다.

지원할 화면:

- 처음 확인된 작성자
- 수집 범위 안에서 다시 댓글을 남긴 작성자
- 댓글 수가 많은 작성자
- 작성자별 댓글·답글과 관련 영상 타임라인
- 마지막 확인 시각
- 크리에이터가 남긴 답글 상태

구독 여부는 댓글 작성자 정보만으로 추정하지 않는다. `최근 구독자`는 공식 API, 필요한 권한, 데이터 공개 범위와 YouTube 정책을 별도로 검증한 경우에만 제공한다.

Audience 집계와 AI 기반 파생 정보는 YouTube 제공값이 아니라 `CrowdSift 분석`이라고 표시한다. YouTube 정책의 데이터 집계·파생 지표 제한에 대한 API Services Audit 또는 전문 검토를 통과하기 전에는 운영 출시 조건으로 삼지 않는다.

## 12. Activity와 대시보드

대시보드는 실제 CrowdSift 작업 이벤트만 사용한다.

- 댓글 가져오기와 재동기화
- 분석 완료·실패
- 답글 초안 생성·수정·게시·실패
- 규칙 일치·승인·건너뜀
- moderation 요청·승인·실패
- 권한 만료, quota 소진과 복구

`활동 추이`와 `상위 규칙`은 CrowdSift가 기록한 이벤트의 집계이며 YouTube 공식 통계가 아니라는 점을 표시한다. 연결되지 않았거나 이벤트가 없으면 0으로 채운 예시 차트를 보여주지 않고 빈 상태와 다음 행동을 보여준다.

## 13. 데이터 경계

기존 수직 슬라이스의 테이블에 다음 책임을 추가한다.

### 13.1 YouTube 출처

- `raw_comments`: YouTube 댓글 ID, 최상위·답글 관계, 최초 확보한 출처 필드
- `raw_comment_payloads`: 변경하지 않는 API 응답 스냅샷
- `youtube_comment_refreshes`: 최신 표시용 필드, 확인 시각, 출처 삭제·비공개 상태와 갱신 결과를 쌓는 append-only 스냅샷
- `youtube_videos`: 영상 ID, 제목, 썸네일 URL과 갱신 시각

최초 출처 스냅샷은 일반 기능에서 수정하지 않는다. 다만 YouTube 정책, 사용자 삭제 요청과 법적 삭제 의무를 피하기 위한 “영구 보존”을 의미하지 않는다. 정책 삭제 경로는 내용을 제거하고 민감하지 않은 최소 감사 표지만 남긴다.

### 13.2 AI와 사용자 판단

- `rule_evaluations`
- `model_runs`
- `comment_analyses`
- `sanitized_feedback`
- `creator_feedback`

출처 데이터와 별도 테이블에 유지한다.

### 13.3 답글

- `reply_templates`: 템플릿 본문, 자리표시자, 범위, 버전
- `reply_drafts`: 직접·템플릿·AI 출처, 생성 입력 참조, 모델·프롬프트 버전, 편집 이력
- `outbound_reply_requests`: 최종 문구, 대상, 확인, 권한, 상태, 멱등성 키와 오류
- `youtube_reply_records`: 성공 응답의 YouTube 답글 ID와 게시 시각

다음 동기화에서 CrowdSift가 게시한 답글을 YouTube 출처 데이터로 다시 받으면 `youtube_comment_id`로 연결하되, 작업 요청과 API 응답 이력은 유지한다.

### 13.4 규칙·활동·Audience

- `automation_rules`: 조건, 작업, 승인 방식, 상태와 버전
- `rule_runs`: dry-run 또는 실제 평가 배치
- `activity_events`: 실제 시스템 이벤트와 민감하지 않은 메타데이터
- `commenter_rollups`: 동일 워크스페이스와 유효한 작성자 채널 ID 범위의 재생성 가능한 집계
- `notification_preferences`, `notification_deliveries`

모든 테넌트 데이터는 `workspace_id`로 격리하고 브라우저에서 제공자 토큰과 서비스 역할 키에 접근하지 못하게 한다.

## 14. 오류와 복구 UX

다음 상태를 명시적으로 설계한다.

| 상황 | 사용자 표시 | 시스템 처리 |
|---|---|---|
| 댓글 사용 중지 | `이 영상은 댓글을 사용할 수 없습니다` | 가져오기 종료, 재시도 버튼 비활성화 |
| 프로필 이미지 없음·실패 | 작성자 이름의 이니셜 아바타 | 이미지 오류가 댓글 전체를 실패시키지 않음 |
| 작성자 채널 ID 없음 | 프로필 링크와 Audience 통합 제한 안내 | 표시 이름으로 동일인 추정 금지 |
| 답글 일부만 포함 | `답글 불러오는 중` | `comments.list(parentId)` 페이지네이션 |
| 답글 불가 | 작성창 비활성화와 이유 | `canReply` 및 부모 상태 확인 |
| 부모 댓글 삭제·비공개 | `YouTube에서 더 이상 답글을 게시할 수 없습니다` | 초안 유지, API 재시도 금지 |
| 읽기·쓰기 권한 철회 | 재연결 또는 추가 권한 안내 | 토큰 사용 중지, 사용자의 다음 행동 대기 |
| quota 소진 | 예상 복구 시각과 미완료 작업 표시 | 자동 무한 재시도 금지 |
| 답글 문구 오류 | YouTube 오류를 안전한 한국어로 표시 | 초안 유지, 수정 후 재확인 |
| 게시 결과 불명 | `게시 여부 확인 중` | 재동기화 후 수동 재시도 |
| AI 실패 | 직접 작성과 템플릿은 계속 사용 가능 | AI 초안만 재시도 |
| 일부 댓글 분석 실패 | 성공 댓글 유지, 실패 항목 표시 | 댓글별 재처리 |

## 15. YouTube 정책·보안 조건

1. YouTube DOM을 스크래핑하지 않고 문서화된 API만 사용한다.
2. 읽기와 쓰기 권한을 분리하고 필요한 순간에 점진적으로 요청한다.
3. 사용자가 승인한 정확한 작업만 수행한다.
4. YouTube 출처 콘텐츠와 CrowdSift 파생 분석을 명확히 구분한다.
5. 저장한 일반 API 데이터는 30일 안에 갱신하거나 삭제하는 작업을 둔다.
6. 연결 철회와 사용자 데이터 삭제 요청을 지원한다. 앱 안에서 받은 삭제·철회 요청은 가능한 즉시, 현재 정책상 늦어도 7일 안에 처리하고, 주기적 권한 확인에서 철회를 발견한 데이터도 정책 기한 안에 제거한다.
7. 토큰, 인증 코드, 유해 원문과 비밀값을 애플리케이션 로그에 남기지 않는다.
8. 프로필 이미지 URL, 댓글과 영상 메타데이터도 YouTube API 데이터로 취급한다.
9. 운영 출시 전에 개인정보처리방침, 이용약관, OAuth 동의 화면과 YouTube API Services 정책 준수를 검토한다.
10. Audience와 파생 대시보드는 데이터 집계·파생 정보 정책에 대한 별도 compliance gate를 통과해야 한다.

## 16. 단계별 구현 순서

### 단계 A — 현재 최우선: 실제 댓글 스레드

- YouTube 연결
- 영상 하나 선택
- 최상위 댓글 20~50개와 가능한 모든 답글 가져오기
- 실제 작성자 이름·프로필 URL·영상 썸네일 저장
- 출처와 AI 결과 분리
- `안전 / 주의 / 위험` 분석
- 선택된 대화 중심 Comment Inbox와 답글 펼치기
- 유해 출처 댓글 기본 숨김

**완료 게이트:** fixture가 아니라 관리 가능한 실제 채널의 데이터가 화면에 정확히 나타난다.

### 단계 B — 실제 답글 운영

- 수동 답글 작성
- 점진적 `youtube.force-ssl` 권한
- 게시 전 명시적 확인
- `comments.insert`
- 결과 ID, 오류, 감사 로그
- 결과 불명 복구와 스레드 재동기화
- 스레드 아래에 붙는 직접 작성 composer와 `게시 전 확인`

**완료 게이트:** CrowdSift에서 확인한 답글 1개가 YouTube의 정확한 스레드에 나타나고 중복 없이 기록된다.

### 단계 C — 템플릿과 AI 초안

- 답글 템플릿·자리표시자·정렬
- AI 초안 2~3개
- 톤 가이드와 동의한 과거 답글 검색
- 재생성·편집·확인
- AI 실패 시 직접 작성 유지

**완료 게이트:** AI나 템플릿이 사용자의 확인을 우회해 게시될 수 없다.

### 단계 D — Rules와 moderation 대기열

- 규칙 작성·버전·dry-run
- 초안 생성, 검토함 이동과 알림
- 승인·수정·건너뜀
- 파괴적 moderation 전에 증거 보존
- 실제 작업·실패·감사 기록

**완료 게이트:** dry-run에는 외부 변경이 없고, 모든 실제 변경에 사용자 확인 기록이 있다.

### 단계 E — Audience와 운영 대시보드

- 작성자 대화 이력
- 신규·재방문·상위 작성자
- 활동 피드
- 작업 추이와 규칙 성과
- 알림 설정

**완료 게이트:** 모든 수치가 실제 source/event에서 재현되며, CrowdSift 파생 정보 표시와 compliance 검토가 끝난다.

## 17. 테스트 전략

### 단위 테스트

- 댓글·답글·프로필 필드 매핑과 nullable 필드
- `textDisplay`와 nullable `textOriginal` 구분
- `totalReplyCount`보다 inline reply가 적을 때 추가 조회
- 안전·주의·위험 표시와 유해 텍스트 가림
- 템플릿 자리표시자 검증
- AI 초안과 외부 게시 요청의 구조적 분리
- reply request 상태 전이
- 동일 워크스페이스 밖 Audience 집계 차단

### 통합 테스트

- 읽기 OAuth와 쓰기 OAuth의 점진적 권한
- top-level 20~50개와 추가 답글 수집
- `comments.insert` 요청 계약과 성공 ID 저장
- OAuth 완료 뒤 자동 게시되지 않고 확인 화면으로 복귀
- 네트워크 timeout 시 자동 중복 게시 방지
- 규칙 dry-run이 외부 API 쓰기를 호출하지 않음
- 답글·moderation 전 사용자 확인과 감사 이벤트

### 브라우저 테스트

- 실제 데이터와 fixture 데이터의 명확한 구분
- 프로필, 영상 썸네일, 댓글과 답글 계층
- 키보드로 필터, 스레드 펼치기, 출처 댓글 경고, 작성·확인 이동
- `1280px`에서 가로 스크롤과 겹침 없음
- 색상 없이 등급을 이해할 수 있음
- 권한·quota·댓글 중지·빈 상태·부분 실패

### 수동 실제 채널 테스트

테스트용 크리에이터 소유 채널과 되돌릴 수 있는 댓글 스레드를 사용한다.

1. 실제 프로필·표시 댓글·답글 수 비교
2. 답글 누락 여부 비교
3. 안전·주의·위험 원문 보호 확인
4. 수동 답글 게시 후 YouTube에서 확인
5. 반환된 YouTube 답글 ID와 DB 기록 비교
6. 같은 요청이 두 번 게시되지 않았는지 확인
7. 권한 철회와 재연결 확인

실제 토큰, 채널 ID, 영상 ID와 댓글 본문은 저장소나 테스트 로그에 기록하지 않는다.

## 18. 출시 승인 기준

- [ ] 실제 최상위 댓글 20~50개와 그 답글을 가져온다.
- [ ] 실제 작성자 표시 이름과 프로필 이미지가 가능한 경우 정확히 나타난다.
- [ ] 프로필·작성자 ID가 없을 때 거짓 정보로 보완하지 않는다.
- [ ] `textDisplay`를 진짜 원문이라고 잘못 표시하지 않는다.
- [ ] 안전 댓글과 주의·위험 댓글의 기본 노출 정책이 다르게 적용된다.
- [ ] 답글 계층과 답글 수가 YouTube 데이터와 일치한다.
- [ ] 사용자가 확인한 최종 문구만 YouTube에 게시된다.
- [ ] OAuth 동의 뒤 답글이 자동 게시되지 않는다.
- [ ] 성공한 답글의 YouTube ID, 시각, 실행자와 상태를 기록한다.
- [ ] 결과 불명 요청을 자동 재시도해 중복 답글을 만들지 않는다.
- [ ] AI 초안, 템플릿, 출처 댓글과 게시 결과를 분리 저장한다.
- [ ] Rules dry-run은 실제 댓글이나 답글을 변경하지 않는다.
- [ ] moderation은 증거 보존과 확인 뒤에만 실행된다.
- [ ] 대시보드는 예시 수치를 실제 운영 수치처럼 표시하지 않는다.
- [ ] YouTube 출처와 CrowdSift 분석을 명확히 구분한다.
- [ ] 데이터 갱신·삭제·연결 철회 흐름이 동작한다.
- [ ] `npm run lint`와 `npm run build`가 통과한다.

## 19. 현재 제외하거나 별도 결정을 요구하는 범위

- YouTube 화면 DOM에 UI를 삽입하는 확장 프로그램
- YouTube 또는 Google 화면 스크래핑
- CommentShark나 YouTube UI의 정확한 복제
- 경쟁사 내비게이션에 있는 랜덤 댓글 추첨, 트렌딩 영상 댓글과 이메일 문구 생성기
- 다른 시청자 댓글의 `textOriginal`이 항상 존재한다는 약속
- 답글 아래에 또 답글이 달리는 진짜 다단계 중첩 구조
- API가 제공하지 않는 dislike, creator heart, pin 상태의 추정
- 댓글 작성자의 구독 여부 추정
- 사용자 승인 없는 자동 답글·자동 숨김·자동 삭제
- 여러 YouTube 채널의 동시 운영
- Instagram·TikTok
- 결제, 요금제와 모바일 앱

승인 없는 자동 외부 작업이나 선택적 확장 프로그램은 이 설계를 조용히 확장하지 않고, 별도 제품 결정과 정책 검토를 거친 새 설계서로 다룬다.

## 20. 구현 계획 전 사용자 승인 항목

이 설계가 승인되면 `superpowers:writing-plans`로 파일·테스트 단위 구현 계획을 작성한다. 그 전에 다음 결정만 확인한다.

1. 첫 쓰기 기능은 `수동 답글 게시`로 확정한다.
2. 템플릿과 AI는 답글 초안만 만들고 매번 사용자가 확인한다.
3. Rules도 초기에는 승인 대기열을 만들며 자동 게시하지 않는다.
4. 선택한 `대화 중심 워크스페이스`를 UI 기준으로 사용하고 CrowdSift 안전 UX와 브랜드를 우선한다.
5. Audience·대시보드는 핵심 댓글·답글 흐름 뒤에 구현한다.
