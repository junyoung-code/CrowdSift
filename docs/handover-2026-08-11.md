# 인수인계 · 2026-08-11

> **2026-08-13 갱신.** 아래 3 절의 「RAG — 없는 것 두 개」는 이어졌다. 개인화가 실제
> UI 로 한 바퀴 돌았고, 그 과정과 결과는 로드맵 15차에 있다. 이 문서에서 아직 유효한
> 것은 1 절(살아 있는 상태)과 4 절(알아 두면 좋은 것)이다.
>
> 여기에 두 가지를 더한다.
>
> - 개발자 도구(`/app/developer-tools`)는 기능 플래그 뒤에 있다. `.env.local` 에
>   `ENABLE_DEVELOPER_TOOLS=true` 와 `DEVELOPER_USER_IDS=<본인 user id>` 가 없으면
>   페이지가 **404 로 사라진다.** 고장이 아니다
> - 브랜치를 갈아타거나 머지한 뒤 모든 경로가 404 라면 `.next` 가 옛 파일 구조를
>   붙들고 있는 것이다. 지우고 `npm run dev` 를 다시 하면 된다

분류 파이프라인 정확도 작업을 일단 멈추고 RAG 로 넘어가는 지점이다. 이 문서는 로드맵의
측정 기록(13·14차)과 겹치지 않는 것만 담는다 — **다른 사람이 이 저장소를 열었을 때
모르면 다치는 것들.**

## 1. 지금 살아 있는 상태 (코드에 안 적혀 있는 것)

### 은어 목록이 비워져 있다

로컬 DB 의 `classification_profiles.allowed_slang` 이 `{}` 다. 콜드 스타트(신규 사용자가
보는 화면)를 재려고 일부러 비운 것이고, **아직 되돌리지 않았다.**

이 상태에서는 「개맛있겠다」 「ㅈㄴ웃기네」 같은 칭찬형 비속어가 전부 주의로 잡힌다.
버그가 아니다. 되돌리려면:

```sql
update classification_profiles
set allowed_slang = '{개웃김,개귀여움,개이쁘다,ㅈㄴ,존나,미쳤다,ㅁㅊ,ㄹㅇ,개}'::text[]
where workspace_id = 'c61e0fb2-97ee-45a1-803f-d628f96611d3'::uuid;
```

RAG 를 붙이고 나면 이 목록은 **개인화 첫 시험대**가 된다. 비운 채로 두고 교정 →
재분석으로 옮겨붙는지 보는 편이 낫다. 되돌리기 전에 한 번 생각할 것.

### 채널 자동 수집은 꺼 둔 채로 둔다

측정 중에 배경 수집이 돌면 같은 댓글의 판정이 여러 벌 쌓여 무엇을 재는지 알 수 없게
된다. 측정이 끝날 때까지 켜지 않는다.

### 브랜치가 원격보다 25개 앞서 있다

`feature/caution-rewrite-wiring` · 아직 push 하지 않았다.

### `npx supabase gen types typescript --local` 을 돌리지 말 것

`src/types/database.ts` 를 통째로 다시 써서 다른 사람 코드가 깨진다. 스키마를 바꿨으면
그 파일을 **손으로** 고친다.

## 2. 오늘 바뀐 것 (3 커밋)

```
db2ad39  비교로 칭찬하는 말을 외모 공격으로 읽던 것        프롬프트 v9
4e4eca4  판단할 거리가 없는 댓글을 검토 대기로 보내던 것    verdict.ts
190027e  사생활 참견을 조언으로 읽던 것                   프롬프트 v10
```

등급 **기준은 건드리지 않았다.** 바뀐 것은 두 가지뿐이다.

- 프롬프트가 기준을 더 정확히 읽게 한 것 (v9, v10)
- 두 판단이 갈렸을 때 무엇을 하는지 (verdict.ts)

전체 세트 기준 50/54 → 53/54. 남은 오답은 B05 「ㄹㅇ 이게 자취요리지」 하나인데,
이것은 은어를 등록하면 정답이 안전으로 바뀌는 문항이라 **개인화가 다룰 자리**다.

### 되돌린 것도 있다 — 같은 생각을 다시 하지 않도록

`danger_in_either`(한쪽만 위험이라 해도 위험) 때문에 2차 검증의 반대 의견이 버려지는
것처럼 보여서, 2차가 위험을 주의로 한 칸 낮출 수 있게 열어 봤다. 69건에서 세 번
걸렸고 셋 다 오지랖이었다. 기준은 사생활 참견을 공격으로 본다.

**즉 2차가 기준 하나를 적용하지 않고 있었고, 그 규칙이 구멍을 메우고 있었다.** 되돌리고
이유를 `src/features/classification/verdict.ts` 의 `resolveDisagreement` 주석에 남겼다.
v10 프롬프트가 그 구멍을 실제로 메웠다(`danger_in_either` 6 → 4).

### 새 측정 도구

```
scripts/run-vlog-pipeline.ts          전체 세트를 파이프라인에 통째로. DB 에 쓰지 않는다
scripts/probe-private-life-meddling.ts   사생활 참견 겨냥. 통제군을 같은 표에 둔다
scripts/probe-comparative-praise.ts      비교 칭찬 겨냥
scripts/report-vlog-run.ts            앱을 거쳐 DB 에 쌓인 것을 읽는다 (모델 호출 없음)
```

앞의 셋은 모델을 부르므로 비용이 든다. 전체 한 판이 약 40만 토큰이다.

프롬프트를 고쳤으면 **겨냥 프로브 → 전체 세트** 순으로 본다. 프로브에는 올라가야 할
문장과 절대 올라가면 안 되는 문장을 반드시 같이 넣는다. 한쪽만 보면 고친 것이 아니라
기준을 무른 것이 된다.

## 3. RAG — 이미 대부분 있다. 연결이 없을 뿐

내일 할 일이고, **팀원이 이미 깔아 둔 것 위에 얹는 작업**이다.

### 있는 것

```
pgvector 확장
public.feedback_embeddings           vector(1536)
public.match_creator_feedback        코사인 유사도 · 워크스페이스 격리
                                     use_for_personalization 게이트 · 최대 5건
src/features/analysis/supabase-rag-repository.ts    RPC 호출부
src/features/analysis/rag-service.ts                검색 서비스
src/features/feedback/feedback-service.ts           교정 저장 + 임베딩 생성 + 공개URL 차단
두 프롬프트의 「유사 사례 반영」 절                     모델이 쓰는 법을 이미 안다
```

### 없는 것 — 둘뿐이다

**① 쓰는 길.** `feedback-service.ts` 를 부르는 코드가 하나도 없다. 그래서
`feedback_embeddings` 에 **한 줄도 들어간 적이 없다.**

**② 읽는 길.** `src/features/classification/classification-work-item.ts:64` 가
`similarExamples: []` 를 넘긴다.

검색 서비스는 `src/features/analysis/process-analysis-job.ts` 에만 연결돼 있는데, 그것은
아무도 부르지 않는 옛 파이프라인이다. 지금 도는 것은
`src/features/classification/classification-service.ts` 다. **스키마만 보면 완성된 것처럼
보이지만 빈 테이블에서 검색하고 있다.**

### 먼저 정해야 할 것 — 교정이 두 테이블로 갈라져 있다

```
인박스 「AI 판단 수정」            → classification_feedback   실제 데이터가 있다
match_creator_feedback 가 읽는 곳  → creator_feedback          아무도 쓰지 않는다
```

같은 것을 담는 테이블이 둘이다. `classification_feedback` 을 남기고 RPC 가 그쪽을 보게
하는 쪽을 제안한다. 인박스가 이미 쓰고 있고, 13차에 교정을 **판정이 아니라 댓글에**
매달도록 고쳐 두어서 재분석해도 사람 손이 사라지지 않는다.

### 붙이는 순서

```
1. match_creator_feedback 이 classification_feedback 을 보게        마이그레이션 1개
2. 인박스 교정 저장할 때 임베딩도 만들기                            feedback-service 연결
3. classification-work-item 의 [] 를 실제 검색으로                  공개 URL 은 제외
4. B 무리로 한 바퀴 — 「개웃김」 하나 교정하고 재분석해서 옮겨붙는지
```

4 번이 진짜 시험대다. 1~3 은 연결이고, 개인화가 실제로 도는지는 거기서 처음 보인다.

**공개 URL 로 들어온 댓글은 검색에서 뺀다.** 제품 규칙이다 — 공개 URL 결과에는 개인화
RAG 를 허용하지 않는다(`docs/product-context.md`). `feedback-service.ts` 에는 이미
`PublicSourceReadOnlyError` 로 막혀 있고, 읽는 쪽에도 같은 게이트가 필요하다.

## 4. 알아 두면 좋은 것

### 유튜브가 계정을 잠근다

댓글 하나가 아니라 **계정 전체**를 API 에서 감춘다. 한 계정의 댓글이 통째로 사라지면
수집 버그가 아니라 이것일 가능성이 높다. 실제로 8/8 이 사라지고 다른 두 계정은
0/8 이었다.

### 유튜브는 답글을 펴서 준다

화면에서는 3단으로 들여쓰기돼도 API `parentId` 는 **항상 최상위**다. 실제 상대는
원문에 남은 `@사용자명` 으로만 알 수 있다. 이것 때문에 K 무리는 구조적으로 틀린다.

### 유튜브가 지우는 것과 우리가 잡아야 할 것이 다르다

욕설·링크는 유튜브가 먼저 지운다. 그런데 「어디 사는지 다 알아냈다 조심해라」는
살아남았다. 우리가 잡아야 할 것이 유튜브가 놓치는 것과 겹친다.

### 판정 흔들림

같은 문장·같은 프롬프트로 판이 바뀌면 등급이 바뀌는 것이 있다. F04 가 두 판 사이에
위험 ↔ 주의로 오갔다. **한 판으로 「고쳤다」고 말하지 않는다.** 경계에 있는 문항은
세 번 돌려 본다.
